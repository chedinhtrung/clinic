# Chatbot Design

This document describes the planned patient chatbot architecture. The chatbot is
not a general public assistant. It is a post-confirmation intake assistant tied
to one confirmed booking.

The purpose is to collect structured patient information before the appointment
and save a concise handoff into `bookings.ai_summary` for the admin page.

Relevant current files:

- `backend/booking/app.py`
- `backend/booking/_booking.py`
- `backend/chatbot/app.py`
- `backend/chatbot/chat_service.py`
- `backend/database/001_bookings.sql`
- `adminpage/components/SlotEditor.tsx`
- `landingpage/app/booking/chat/page.tsx`
- `landingpage/components/BookingChat.tsx`

## Core Idea

Each confirmed booking has its own independent chatbot conversation.

The frontend may only open the chat when it has a valid signed chat token for a
confirmed booking. The token identifies the booking, but the database remains
the source of truth for whether the booking is still allowed to chat.

This means cancellation and rescheduling are handled by normal booking state:

- the token proves that the link was issued by the backend
- the booking row proves that the link is still allowed right now

If a patient cancels a booking, the booking status changes to `cancelled`.
Future chat requests with the old signed token are rejected because the booking
is no longer `confirmed`.

## Chat Access Token

The chat link should contain a signed token generated by the backend after a
booking is confirmed.

The token should be signed with a dedicated secret, for example:

```text
CHAT_TOKEN_SECRET
```

The chat token secret should be separate from:

- admin session secrets
- booking session cookie secrets
- email confirmation token secrets
- payment secrets

Version 1 keeps the token payload minimal and signs only the booking id.

The token expiration should be derived from the appointment date. A reasonable
default is the end of the appointment day in the clinic timezone. If the clinic
wants intake to close earlier, expiration can be set to the appointment start
time instead.

The backend should not trust the token expiration as the only time rule. On each
message, the backend should also load the current slot and compute whether chat
is still allowed for the booking's current appointment time.

## Authorization Rule

Every chat request should perform two authorization steps.

First, verify the token:

1. Signature is valid.
2. Signed booking id is present and valid.

Second, verify the current booking state from the database:

1. Booking exists.
2. Booking status is `confirmed`.
3. Booking has a linked slot.
4. Current time is inside the allowed chat window for that slot.

The token identifies the booking. The database decides whether that booking may
chat right now.

This database check is intentionally done on every message. The request already
needs database access to load and save conversation memory, and the OpenAI API
call will dominate latency and cost. The check keeps cancellation, rescheduling,
and finished appointments correct without a separate token revocation system.

## Revocation

Version 1 does not need a token registry.

Revocation is handled by database state:

- `cancelled` bookings cannot chat
- `expired` bookings cannot chat
- `finished` bookings cannot chat
- `pending` bookings cannot chat
- only `confirmed` bookings can chat

If explicit revocation is later needed without cancelling the booking, add one
of these fields to `bookings`:

```text
chat_revoked_at timestamptz
```

or:

```text
chat_token_version integer NOT NULL DEFAULT 1
```

With `chat_token_version`, the signed token includes the version. Incrementing
the database version invalidates older tokens.

## Conversation Storage

The simplest version can store the conversation directly on the booking row as a
JSONB list.

Possible fields:

```sql
ALTER TABLE bookings
ADD COLUMN chat_messages jsonb NOT NULL DEFAULT '[]'::jsonb,
ADD COLUMN chat_status text NOT NULL DEFAULT 'active';
```

Each message can be stored as:

```json
{
  "role": "user",
  "message": "Đau gối phải khoảng 2 tuần",
  "created_at": "2026-05-01T12:34:56Z"
}
```

Assistant messages use the same shape:

```json
{
  "role": "assistant",
  "message": "Dạ, cơn đau bắt đầu đột ngột hay tăng dần ạ?",
  "created_at": "2026-05-01T12:35:02Z"
}
```

This is acceptable for version 1 because each booking has one short intake
conversation and the admin page primarily needs the final `ai_summary`.

If conversation querying, auditing, or high concurrency becomes important, move
messages into dedicated tables:

```text
chat_sessions
chat_messages
```

## Request Flow

The chat endpoint should be synchronous for version 1.

Recommended flow:

1. Frontend sends patient message plus signed chat token.
2. Backend verifies the token signature and claims.
3. Backend starts a short transaction.
4. Backend loads the booking and slot.
5. Backend verifies that chat is still allowed.
6. Backend appends the patient message to `chat_messages`.
7. Backend commits the transaction.
8. Backend calls the OpenAI API with the system prompt and saved conversation.
9. Backend starts a second short transaction.
10. Backend appends the assistant reply to `chat_messages`.
11. If intake is complete, backend writes the final summary to
    `bookings.ai_summary` and sets `chat_status` to `finished`.
12. Backend commits the transaction.
13. Backend returns the assistant reply to the frontend.

The OpenAI call should happen outside a database transaction. This avoids
holding a row lock while waiting for a network call.

The assistant response should be saved before returning it to the user. That
keeps the visible chat and persisted memory consistent if a later request loads
the conversation again.

## Concurrency

The frontend should disable the send button while a message is in flight.

The backend should still protect against concurrent writes. Two browser tabs or
double submissions could otherwise load the same JSON list, append different
messages, and overwrite one another.

For JSONB-on-booking storage, use one of these patterns:

- append inside a transaction after selecting the booking row `FOR UPDATE`
- append with a SQL `jsonb || ...` update

The row lock should be held only for the quick database read/update, not during
the OpenAI call.

## OpenAI Response Shape

The model should not return only free-form text to the backend. The backend
should ask for a structured response that separates the visible patient reply
from internal state.

Suggested internal shape:

```json
{
  "role": "assistant",
  "message": "Dạ, hiện tại cơn đau của mình ở vị trí nào rõ nhất ạ?",
  "status": "active"
}
```

When the intake is complete:

```json
{
  "role": "assistant",
  "message": "Em đã ghi nhận thông tin và sẽ chuyển cho bác sĩ Nghĩa trước buổi hẹn ạ.",
  "status": "finished"
}
```

The backend stores:

- `message` as the assistant chat message
- `status` into `bookings.chat_status` when it is `finished` or `abuse`
- a separately generated summary into `bookings.ai_summary` when `status` is
  `finished`

## Assistant Scope

The assistant should behave as a clinic intake assistant in Vietnamese.

Allowed:

- collect musculoskeletal history
- ask one question at a time
- ask about symptoms, onset, injury, severity, function, prior imaging, medical
  history, medication history, allergies, work, sport, and daily activity impact
- summarize information for the doctor
- explain that the doctor will assess the patient during the appointment

Not allowed:

- diagnose the condition
- recommend medication
- recommend imaging or procedures as a medical instruction
- replace the doctor
- answer unrelated medical topics beyond the clinic scope

The assistant may give urgent-care escalation language for obvious red flags,
such as severe trauma, fever with joint swelling, progressive weakness, loss of
bowel or bladder control, or other symptoms that should not wait for routine
intake.

## Admin Output

The admin-facing artifact is `bookings.ai_summary`.

The admin page already reads and displays `ai_summary` for booked slots. The raw
conversation can remain hidden in version 1 unless there is a specific review
need.

The summary should be concise, structured, and clearly marked as patient-provided
information rather than a diagnosis.

## Version 1 Recommendation

Build the first version with:

- signed chat token
- database authorization on every message
- one JSONB conversation list on `bookings.chat_messages`
- synchronous save-user, call-model, save-assistant flow
- final summary written to `bookings.ai_summary`
- chat available only for `confirmed` bookings within the allowed appointment
  window

This keeps the architecture small while preserving the important safety property:
the token grants access to a booking, but the booking row remains the live source
of truth.
